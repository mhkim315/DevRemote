# M3-auth-1B Implementation Report — iOS Secure Enclave DeviceKey Provider

Status: **READY FOR INDEPENDENT VERIFICATION**

Branch: `feature/phase10-multi-adapter`

Baseline: builds on the accepted M3-auth-R1 (`a834955c1`), itself a descendant of
M3-auth-4A (`b34c335`).

This phase replaces the fail-closed iOS DeviceKey stub with a real **iOS Secure
Enclave** provider whose output is byte-identical to the accepted Android
provider, so the shared JS validator and the Go daemon accept an iOS device with
**no daemon change**. Scope is the DeviceKey provider only; iOS pairing / bearer /
WS-ticket / Terminal (M3-auth-2B) is out of scope.

## 2. Exact native contract (reproduced byte-for-byte)

| Aspect | Android (accepted) | iOS (this phase) |
|---|---|---|
| Curve / key | P-256 EC in AndroidKeyStore | P-256 EC in Secure Enclave (`kSecAttrTokenIDSecureEnclave`) |
| Sign | `SHA256withECDSA` → ASN.1 DER | `SecKeyCreateSignature(.ecdsaSignatureMessageX962SHA256)` → X9.62 DER |
| SPKI | `pub.encoded` (91-byte X.509 SPKI) | 26-byte P-256 header + 65-byte `SecKeyCopyExternalRepresentation(pub)` point |
| deviceId | `hex(sha256(SPKI))` | `hex(sha256(SPKI))` |
| Non-exportable | `priv.encoded == null` | `SecKeyCopyExternalRepresentation(priv) == nil` |
| Errors | `DeviceKeyException(code)` → `CodedException` | `DeviceKeyError(code)` → `Promise.reject(code, …)` |
| provider / level | `android_keystore` / `tee`\|`strongbox` | `ios_secure_enclave` / `secure_enclave` |

Because the iOS wire format equals the Android one, and the daemon verifies both
with `ecdsa.VerifyASN1` over `SHA256(transcript)` and `Fingerprint = sha256(SPKI)`
(`internal/devicetrust/{identity.go,auth_handlers.go}`), the daemon accepts iOS
unchanged.

## 3. Provider behavior (fail-closed, mirrors Android)

- `getSupport()` → `"supported"` when `SecureEnclave.isAvailable`, else
  `"hardware_unavailable"` — no software-key fallback.
- `ensureKey()` is atomic; **ownership rule**: only an **exact `key_missing`**
  grants this call creation ownership. An inaccessible/invalidated existing
  identity is never mistaken for "absent" (it propagates without generating or
  deleting), so a locked device can neither regenerate nor roll-back-delete a
  real paired key. A key generated by *this call* is the only thing rolled back
  on validation failure.
- `hasKey()` reports **existence only**: exact `key_missing` → `false`; an
  inaccessible/invalidated/native error propagates as a typed exception (never
  hidden as `false`), so the UI cannot be pushed into a false re-provisioning
  path. The module routes it through the coded Promise so JS sees `error.code`.
- Secure-Enclave key-generation failures are mapped to a **safe typed code**
  without leaking raw provider detail: device-locked/auth → `key_inaccessible`;
  enclave unavailable → `hardware_unavailable`; anything else →
  `native_operation_failed`.
- `validate()` is the single authoritative path used by ensureKey/getKeyInfo/
  getPublicKeySpki/sign: asserts EC / P-256 / Secure-Enclave token, proves
  non-exportability, builds the canonical 91-byte SPKI, computes deviceId. A
  non-enclave / non-P256 / exportable key can never sign.
- Typed error codes are drawn from the shared vocabulary; JS
  `normalizeNativeError` reads `error.code`, unknown → `native_operation_failed`.

## 3a. Remediation after independent REJECT of 748b92ca5

The first submission (`748b92ca5`) was correct on the crypto wire contract but
was rejected for identity-ownership handling and an unrunnable native gate. All
findings are fixed here (iOS store + gate + tests only; shared TS, Android, and
the daemon protocol are unchanged):

- **BLOCKER 1** — `ensureKey` no longer treats any `loadPrivateKey` failure as
  "absent"; only an exact `key_missing` takes creation ownership, so an
  inaccessible existing identity is preserved (no regenerate, no rollback delete).
- **BLOCKER 2** — `hasKey()` is now `throws`: only `key_missing` → `false`; other
  errors propagate typed, and the module rejects the Promise with the code.
- **BLOCKER 3** — `SecKeyCreateRandomKey` CFError is mapped to a safe typed code
  (`key_inaccessible` / `hardware_unavailable` / `native_operation_failed`)
  instead of a blanket `hardware_unavailable`.
- **BLOCKER 4** — `scripts/ios-native-gate.sh` now selects a physical device by
  UDID and runs `-destination "id=$UDID"`, **fails** (not warns) when no device
  is present, and verifies the test scheme via `xcodebuild -list`. A
  generic/build-only or Simulator run is never accepted as a hardware PASS.
- **Regression tests** — new XCTest cases prove an existing incompatible key
  survives every rejection (getKeyInfo/getPublicKeySpki/sign/ensureKey), that
  ensureKey never deletes/regenerates it, and that `hasKey` reports a
  present-but-unusable key as `true` (never hidden as `false`).

Standalone `xcrun swiftc -typecheck PokitDeviceKeyStore.swift` PASS after the fix.

## 3b. Remediation after the second REJECT (native gate + hardening)

The security-logic fixes above were accepted; the second REJECT was that the
XCTest was not actually installable/runnable, because CocoaPods does **not**
install a `test_spec` unless the Podfile opts in with `:testspecs`. Fixed:

- **Native gate now creates the test target.** `scripts/ios-native-gate.sh`
  injects `pod 'PokitDeviceKey', :path => '../modules/pokit-device-key/ios',
  :testspecs => ['Tests']` into the generated Podfile (after `expo prebuild`,
  before `pod install`, idempotently), so the `PokitDeviceKey-Unit-Tests` scheme
  is actually generated. The podspec keeps the `test_spec 'Tests'` declaration.
- **The gate proves execution, not just presence.** It fails if the scheme is
  missing, if `Executed 0 tests`, or if the required enclave test
  (`testSignatureVerifiesWrongKeyAndTamperFail`) did not run+pass — so a run
  where the enclave tests merely skip (Simulator / no device) can never be
  reported as a hardware PASS. Runs on `-destination "id=<UDID>"`.
- **Rollback-cleanup hardening** (recommended alongside): if `ensureKey`'s
  rollback `SecItemDelete` of a freshly-created key fails, that is promoted to
  `native_operation_failed` (an unusable alias must not be masked by the original
  validation error), matching the Android contract.

Verified here: `sh -n scripts/ios-native-gate.sh` PASS (syntax);
`xcrun swiftc -typecheck PokitDeviceKeyStore.swift` PASS; full `build-gate.sh`
PASSED. The gate's actual device execution remains M-track (requires a Mac with
Xcode + a connected iPhone; not available in this environment).

## 3c. Remediation after the third REJECT (gate exit-code capture)

The third REJECT was a false-PASS risk: `xcodebuild test ... 2>&1 | tee "$LOG";
XC_STATUS=$?` in POSIX `/bin/sh` (no `pipefail`) captures **tee's** exit (0), not
xcodebuild's — so a failing XCTest could be masked as a PASS as long as the
required-test string appeared in the log. Fixed: the gate now redirects to the
log (`>"$LOG" 2>&1`), captures xcodebuild's real exit code, then prints the log;
a `trap` removes the temp log on exit.

Independently reproduced (POSIX `/bin/sh`): `(exit 42) | tee log` → `$?` = `0`
(the bug); `(exit 42) >log 2>&1` → `$?` = `42` (the fix). `sh -n` PASS.
