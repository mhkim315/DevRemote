## 1. Authority owner and canonical inputs

- **Store** (`AuthoritativeApprovalStore`) remains the sole owner of claim,
  idempotency, requester authority and commit. P2A adds ONE narrow additive
  capability (§2 below): it can carry daemon-generated immutable delivery
  material per certified option and return the exact stored bytes from
  `ClaimForExecution`.
- **Pump** (`codexManagedRuntime.pump`) remains the only provider stdout
  reader. P2A adds a pump-owned bounded **resolved router**: an exact
  `serverRequest/resolved` is routed to at most one armed per-runtime
  pending-response waiter; everything else falls through to the P1
  display-invalidation path.
- **Delivery boundary** (`codexManagedApprovalDelivery`, new): the ONLY
  component that writes a provider approval response, and only through the
  runtime's owned transport under `writeMu`. It is constructed in P2A but
  **not wired into production** (`Handlers.ApprovalDelivery` stays
  `NewGatedApprovalDelivery` at capacity 0); P2B installs it atomically.
- Canonical inputs of one delivery: the store-granted claim (token, immutable
  binding, EXACT payload bytes), the current runtime resolved by SessionID +
  epoch, and the P1 pending provider-request record holding the preserved
  native id token. The public ApprovalID is never parsed back into a native
  id.

## 2. Minimal A1-core extension (contract §4) — additive, optional

- `ApprovalDeliveryMaterial{OptionID, SchemaVersion, ResponseBytes}` may be
  supplied per option at ingestion. Validation fails the ITEM closed:
  material on a non-actionable item; an option ID with no matching stored
  option; duplicate material for one option; empty/oversized bytes
  (1..4096); empty/oversized schema version.
- The store defensively copies material into the record; material is
  included in the option-set fingerprint (a same-ID re-offer with different
  material is not the same request) and in the canonical action digest
  (`CanonicalAction` gains `DeliverySchemaVersion` + `DeliveryPayloadDigest`,
  both length-prefixed into `Digest()`).
- `ClaimForExecution` returns a defensive copy of the EXACT stored bytes as
  the claim payload when the selected option has material;
  `Binding.PayloadDigest` is the digest of those exact bytes and is carried
  unchanged through delivery receipt and commit (frozen R3-B substitution
  rejection applies as-is).
- Records without material keep the frozen legacy behavior byte-for-byte.
  No public/mobile DTO carries material, schema versions, or response bytes.
- This extension is NOT a provider SDK and does not authorize generic
  commands: bytes are opaque store-carried payloads generated by the daemon
  at ingestion time.

## 3. Resolved-message hardening (P1-accepted follow-up, reviewer-mandated)

`observeApprovalResolved` now enforces, before any routing:

- whole-message byte bound (`maxResolvedMessageBytes` 4096) — first check;
- strict closed-field decode at envelope (`jsonrpc`/`method`/`params`) and
  params (`threadId`/`requestId`) with duplicate-key/trailing rejection;
- REQUIRED `jsonrpc == "2.0"`;
- params byte bound (`maxResolvedParamsBytes` 1024);
- exact thread binding and integer-grammar requestId token.

A resolved failing any check is inert for BOTH the router and the P1
invalidation path.

## 5. Delivery linearization (contract §5)

`Deliver` returns `DeliveryAccepted` ONLY after this exact sequence:

1. binding metadata validated (frozen `validGateBindingMeta` grammar) and the
   payload re-digested: `payloadDigest(req.Payload) == Binding.PayloadDigest`
   or reject with ZERO writes;
2. current runtime revalidated (session, epoch==LaunchGen, StreamGen 0,
   adapter `codex_app_server`, pinned authority version, registry record not
   exited);
3. the P1 pending provider-request record for `Binding.ApprovalID` is looked
   up under `turnMu`; missing → unavailable (a provider request that is
   already resolved/expired can never be written to); the payload's
   top-level id token must equal the preserved native token;
4. a waiter is armed under `respMu` (duplicate native id → conflict; bounded);
5. re-check under `respMu` that the waiter was not already consumed, then the
   EXACT bytes are written once through the owned transport (`writeMu`), and
   `written=true` is set under `respMu` after the write returns;
6. the pump routes a matching resolved to the waiter: observed with
   `written=true` → success; observed with `written=false` → provider-side
   resolution, NOT success (write is then skipped);
7. the receipt carries the claim token, full binding, opaque ReceiptID and
   `DeliveredPayloadDigest` of the exactly-written bytes; the store commits
   via the frozen `RecordDelivery`.

Queue admission does not exist on this path: there is no queue. Timeout
(bounded, injectable) closes the waiter and returns the ambiguous
non-retryable outcome (`conflict`) — a LATE resolved then finds no waiter and
falls to the P1 path, which cannot commit (the record is no longer pending).
Pump exit deterministically fails every armed waiter (`stale_runtime`).

**Honest ordering caveat**: the linearization point is "resolved OBSERVED
strictly after the exact write" (contract §5 wording). A provider-side
cancellation whose resolved is emitted concurrently with our write and
observed after it is indistinguishable at the wire level (the provider emits
no error for ignored late responses — CP0 finding). The armed/written
mechanism eliminates every sequenced case (resolved consumed before arm →
no waiter; observed before write → failure with write skipped); the residual
window is the simultaneous emission race inherent to the protocol.

## 7. Adversarial interleavings (one per critical invariant)

1. **Write-before-resolved**: happy path asserts, via the scripted provider,
   that exactly ONE write of exactly the claim bytes precedes the resolved,
   and commit yields `approved`.
2. **Payload substitution**: tampered bytes with the real claim token →
   boundary digest check rejects BEFORE any write; store commit path
   separately rejects a receipt with a substituted delivered digest.
3. **Pre-write resolved (cancel)**: (a) resolved consumed before Deliver →
   arm fails, zero writes, no success; (b) resolved routed between arm and
   write (deterministic barrier) → waiter fires `written=false`, the write is
   SKIPPED, receipt is failure, record ends `delivery_failed`.
4. **Duplicate**: a second Deliver for the same native id while armed →
   conflict, zero additional writes.
5. **Timeout + late resolved**: no resolved within the injected bound →
   ambiguous non-retryable failure; a resolved arriving after timeout finds
   no waiter and cannot commit or resurrect the record.
6. **Exit/replacement**: child killed while waiting → waiter closed
   deterministically, `stale_runtime`; a binding with a stale epoch or a
   deleted session never reaches the write.
7. **Malformed resolved**: missing/wrong `jsonrpc`, oversized message/params,
   unknown field, duplicate key, wrong thread, non-integer requestId — each
   is inert (the armed waiter survives and a subsequent EXACT resolved still
   succeeds, proving non-vacuity).
8. **Material integrity**: caller-side mutation of the ingested material
   slice does not alter the stored bytes; two records differing only in
   material have different action digests; material never appears in
   `ListSafe`/`List`/managed rows JSON.

## 10. R1 amendments (reviewer blockers on fcd702d, both remediated)

1. **Write-claim linearization**: the waiter is now a closed state machine
   `armed → write_claimed → written`, with EVERY transition — the pump's
   resolved routing, the deliverer's write claim and written mark, and the
   exit close — happening under the ONE respMu linearization point, while no
   lock is held across the external write.
   - A resolved that wins the claim race (state `armed`) makes the write
     UNPERFORMED: zero provider bytes (the old check-then-write window is
     gone).
   - A resolved routed while the write is claimed (state `write_claimed`) is
     the new `waiterResolvedDuringWrite` outcome: the single write happened,
     the receipt is the ambiguous non-retryable `conflict`, so a bounded
     manual retry — which could duplicate the write — is impossible
     (`retry_exhausted` proven).
   - The written mark set-window (write returned, mark pending) routes as
     during-write: a possible success is reported as ambiguous failure, never
     the reverse.
   - Stop/kill/exit race the SAME transitions via the respMu-owned close.
   - Evidence: `TestCodexDelivery_KnownBadCheckThenWriteControl` reproduces
     the pre-remediation race against the real structures (write lands after
     the resolved consumed the waiter) — proving the harness catches the
     defect; barrier tests at `post-arm` (zero writes) and `post-write-claim`
     (one write, ambiguous, non-retryable; exit variant → stale_runtime).
   - Test determinism note: on the in-process pipe the fake provider's
     inline auto-resolve is a rendezvous with the write syscall, so it can
     race the written mark — which the production semantics CORRECTLY
     classify as during-write ambiguity. Happy-path tests therefore inject
     the resolved at the `post-written-mark` barrier (the real-pipe ordering,
     where write-return precedes provider processing), keeping the ambiguous
     classification intact in production while making every test outcome
     deterministic (proven stable at 100 repetitions under -race).
2. **Exact action↔response semantic coupling**: the immutable
   `ApprovalExecutionBinding` gains INTERNAL fields `OptionID` (store-selected
   action identity) and `DeliverySchema` (material schema identity), set by
   the store at claim time, compared by `equal` through claim → delivery →
   receipt → commit, cloned/bounded/accounted at the legacy gate, and never
   projected into any public/mobile DTO. The Codex boundary now
   strict-decodes the response to EXACTLY
   `{jsonrpc:"2.0", id:<integer>, result:{"decision":<string>}}` (no unknown
   or extra fields, no duplicate keys) and admits ONLY the certified mapping
   `allow_once → accept` / `deny → decline` under the certified schema
   identity `codex.appserver.decision.v1` — a swapped option↔response ingest,
   a non-certified schema, an extra result field, an unknown/amendment/cancel
   decision, or a tampered binding option/schema is rejected BEFORE the wire
   with zero writes, and a forged accepted receipt carrying a tampered
   binding cannot commit.
