## Summary

`abb32a07d` adds three optional agent fields to `term.SessionTelemetry`:

- `agentKind`
- `agentStatus`
- `agentConfidence`

It also updates the boundary test to marshal a real `SessionTelemetry` value containing
Claude adapter output. This is an improvement over the previous `mockActivity` test.

However, Phase A5 still cannot be accepted. The new fields are not populated by the real
telemetry/API path. The test manually constructs a `SessionTelemetry` instance and fills
the new fields itself. That proves the struct can serialize those fields, but it does not
prove that Claude adapter output actually flows through production telemetry, API, or
mobile boundaries.

## Positive findings

### 1. Real `SessionTelemetry` type now has optional agent fields

This is a useful product-boundary schema step and is backward compatible because the
fields are tagged `omitempty`.

### 2. The boundary test no longer uses a separate mock schema

`TestClaudeOutput_ProductBridge` now marshals the real `SessionTelemetry` type rather
than a local `mockActivity`.

### 3. Existing API tests still pass

The optional fields did not break existing backend tests.

## Blocking issues

### P0 — The real telemetry snapshot path does not populate the new fields

`TelemetryService.Snapshot` still builds `SessionTelemetry` without setting:

- `AgentKind`
- `AgentStatus`
- `AgentConfidence`

`buildSimpleSnapshot` also omits those fields.

The new test manually does this:

```go
st := SessionTelemetry{
    AgentKind:       id.Kind,
    AgentStatus:     string(result.Status),
    AgentConfidence: id.Confidence,
}
```

That is not the production path. The accepted A5 requirement is that Claude adapter
output reaches the product boundary, not merely that a test can manually copy fields into
the boundary type.

### P0 — `internal/agent` output is still not bridged into existing telemetry/events

Repository search shows `agent.NewClaudeParser`, `agent.NewClaudeDetector`, and
`agent.NewClaudeLogResolver` are used by tests, not by production telemetry or API code.

The existing telemetry service still uses:

- `internal/term.AgentLogParser`
- `internal/term.ClaudeParser`
- `internal/models.AgentEvent`
- `EventStore` / `SessionTelemetry.Events`

The new `internal/agent.ParseResult`, `agent.AgentEvent`, and `agent.AgentApproval` are
not converted into:

- `models.AgentEvent`
- `EventStore`
- `/api/sessions` response generated by `TelemetryService.Snapshot`
- history/activity API
- mobile-visible events or approval state

### P0 — Mobile boundary is not updated or tested

The backend now emits optional JSON keys if manually populated, but the mobile
`SessionTelemetry` TypeScript interface still has no:

- `agentKind`
- `agentStatus`
- `agentConfidence`

There is also no mobile test or mobile-facing schema golden proving unknown/new agent
fields are accepted and displayed safely.

Because Phase A5 originally included mobile/product boundary behavior, this remains
incomplete.

### P1 — Agent status values do not match existing mobile state taxonomy

The test sets:

```go
State: string(result.Status)
```

`agent.AgentStatus` includes values such as:

- `waiting_approval`
- `waiting_input`
- `completed`
- `failed`
- `interrupted`
- `degraded`

The existing mobile `SessionTelemetry.state` union is:

```ts
'idle' | 'thinking' | 'working' | 'waiting'
```

So `State: string(result.Status)` is not a safe product mapping. `AgentStatus` may be a
separate field, but existing `State` must remain in the terminal/mobile taxonomy unless
the mobile model is updated.

### P1 — Failure isolation is still weakly tested

The test confirms `/api/sessions` succeeds with no agent layer involved. It does not
simulate:

- parser failure;
- resolver degraded result;
- detector low-confidence unknown;
- conversion failure from `agent.ParseResult` to telemetry;
- terminal session continuing while agent parsing fails.

### P1 — Resolver/cursor/approval identity remain unresolved

Previous issues remain:

- resolver still synthesizes paths from `ev.CWD` and does not prove real A1 log
  discovery;
- cursor still embeds raw first-line prefix and is collision-prone;
- approval IDs are batch-level, not stable per approval.

These are not the primary reason for rejection, but they still block production-quality
exposure.

## Required next changes

To accept Phase A5 under the original product-boundary standard:

1. Add a real production bridge from `internal/agent` to telemetry:
   - detect agent identity from session/process evidence;
   - resolve logs;
   - parse logs;
   - convert agent output into existing `SessionTelemetry` and/or `models.AgentEvent`.
2. Populate `AgentKind`, `AgentStatus`, and `AgentConfidence` in
   `TelemetryService.Snapshot` or the telemetry sampling path from actual adapter output.
3. Add API tests that call `/api/sessions` and observe Claude-derived agent fields in the
   actual handler response, without manually constructing `SessionTelemetry`.
4. Add conversion tests for `agent.AgentEvent` / `agent.AgentApproval` into the current
   product model, or explicitly extend the product model and mobile schema.
5. Update mobile TypeScript types and add a mobile-facing schema/golden test for the new
   fields.
6. Map `agent.AgentStatus` to terminal/mobile `state` safely, or keep it separate and
   prove existing state values remain valid.
7. Add failure-isolation tests where parser/resolver/detector failures degrade agent
   telemetry but do not break terminal sessions.
8. Fix resolver discovery, cursor generation, and approval ID stability before exposing
   this path as production behavior.

## Current judgment

`abb32a07d` is a meaningful schema step, but it is still not a completed Phase A5
vertical slice. The bridge is represented in a test by manual assignment, not implemented
in the production telemetry/API/mobile path.

Do not proceed to Phase A6 until actual product-boundary population is implemented or
the plan is explicitly revised to accept this as a narrower pre-A5 milestone.
